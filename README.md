# ESP32 iPixel Color BLE Bridge

Turn an ESP32 into a Wi-Fi bridge for a flexible LED sign (sold under names like
**Laralov**, and others) that is normally driven by the **iPixel Color** phone
app over Bluetooth LE.

The ESP32 connects to the sign over BLE exactly as the phone app would (BLE
*central*), and serves a small web page + JSON API over Wi-Fi so you can control
the sign from any browser on your network — no app required.

```
  Browser  ──HTTP──▶  ESP32  ──Bluetooth LE──▶  LED sign (iPixel Color)
```

## Features

- Scan for and connect to `LED_BLE_*` signs
- Power on/off, brightness, clear
- Set an individual pixel (RGB + x/y)
- **Scrolling text** with colour, animation, and speed (embedded 8×16 ASCII font)
- Raw-frame passthrough for debugging / per-device protocol tweaks
- Wi-Fi station mode with an access-point fallback and a web config form

## Hardware

- An **ESP32-S3** dev board is recommended (more RAM for BLE + Wi-Fi together);
  a classic **ESP32** also works.
- No wiring to the sign — the bridge talks to it wirelessly. The sign keeps its
  own controller; this project does **not** drive LEDs directly.

## Build & flash

This is a [PlatformIO](https://platformio.org/) project (works from the CLI or
the VS Code extension).

```bash
pio run -e esp32-s3 -t upload   # ESP32-S3
pio run -e esp32dev -t upload   # classic ESP32
pio device monitor              # serial log @ 115200
```

## First run

1. After flashing, the board starts a Wi-Fi hotspot **`iPixelBridge`**
   (password `pixel1234`). Join it and open **http://192.168.4.1/**.
   (To put it on your home network instead, enter your SSID/password in the
   **Wi-Fi** card and reboot; it then joins in station mode.)
2. **Close the official iPixel Color app** — the sign accepts only one BLE
   connection at a time (see Caveats).
3. Tap **Scan**, connect to your `LED_BLE_*` sign, then try **Power on**,
   **Brightness**, and **Scrolling text**.

## HTTP API

All POST bodies are JSON. Responses are `{"ok":true}` or `{"ok":false,"error":"…"}`.

| Method | Path | Body |
| --- | --- | --- |
| GET  | `/api/status` | — |
| GET  | `/api/scan` | — (blocks ~5 s) |
| POST | `/api/connect` | `{"address":"aa:bb:…","type":0}` |
| POST | `/api/disconnect` | — |
| POST | `/api/power` | `{"on":true}` |
| POST | `/api/brightness` | `{"level":0-100}` |
| POST | `/api/clear` | — |
| POST | `/api/pixel` | `{"r":255,"g":0,"b":0,"x":0,"y":0}` |
| POST | `/api/text` | `{"text":"hi","r":255,"g":128,"b":0,"anim":1,"speed":80}` |
| POST | `/api/raw` | `{"hex":"05 00 07 01 01"}` |
| POST | `/api/wifi` | `{"ssid":"…","pass":"…"}` (saves to NVS, reboots) |

Animations: `0` static, `1` scroll-left, `2` scroll-right, `3` up, `4` down,
`5` blink, `6` fade, `7` snowflake.

## Protocol provenance & accuracy ⚠️

The iPixel Color BLE protocol is **not official** — there is no vendor spec.
The command bytes here were ported from community reverse-engineering projects:

- [`lucagoc/pypixelcolor`](https://github.com/lucagoc/pypixelcolor) (primary reference)
- [`yyewolf/go-ipxl`](https://github.com/yyewolf/go-ipxl)
- [`cagcoach/ha-ipixel-color`](https://github.com/cagcoach/ha-ipixel-color) (protocol doc)

GATT layout used: write characteristic `0000fa02-…`, notify `0000fa03-…`; the
service UUID is discovered at runtime. These were **read from source, not
captured from a device**, so treat every command as a strong hypothesis until
you confirm it on your own sign.

If a command does the wrong thing on your unit:

1. Command bytes live in one place — `include/config.h` (opcode constants) and
   the small builders in `src/ipixel.cpp`. A correction is usually one line.
2. Use the **Raw frame** box in the web UI (or `POST /api/raw`) to try bytes by
   hand, and watch `last notify` on the status line for the device's replies.
3. To capture ground truth, record an Android **Bluetooth HCI snoop log** while
   using the official app, and compare.

### Text rendering

Text is rendered on the ESP32 with an embedded **8×16 ASCII** font
(`include/font8x16.h`, generated by `tools/genfont.py`). This matches the common
16-px-tall sign. Notes:

- Only printable ASCII (0x20–0x7E) is included; other characters render as `?`.
- Taller signs (32 px) or CJK/emoji glyphs are **not** supported — those need a
  larger font or the app's Unifont/Pillow renderer. Regenerate the font with
  `tools/genfont.py` for a different face.

## Caveats

- **One BLE connection at a time.** While the bridge is connected, the official
  app can't connect (and vice-versa). Power the ESP32 down to use the app again.
- **BLE + Wi-Fi share the 2.4 GHz radio and RAM.** It's comfortable on an
  ESP32-S3; on a classic ESP32 it works but is memory-tight (hence the
  large-app partition in `platformio.ini`).
- **No authentication on the web UI.** Anyone on the same network can control
  the sign. Keep it on a trusted network.
- Image/GIF upload, clock mode, and the OTA/auth channel are **not** implemented
  (documented stretch goals).

## Project layout

```
include/config.h      Wi-Fi, BLE filter, UUIDs, command opcodes (edit here)
include/font8x16.h    embedded ASCII font (generated)
src/ipixel.*          BLE central + command/frame builders + CRC32 + text
src/web.*             HTTP server + JSON API
src/index_html.h      the control page (served from flash)
src/main.cpp          Wi-Fi bring-up + wiring
tools/genfont.py      regenerate the font
```
